Recon من الـ HTML والـ JavaScript

قبل أي payload، الـ pentester المحترف بيرسم خريطة سطح الهجوم: كل صفحة، كل parameter، كل endpoint، كل host، وكل حاجة «مكنش المفروض تبقى هنا». وأغلب الخريطة دي موجودة في الكود اللي السيرفر بيبعته لك بنفسه. في الدرس ده هنحوّل كل اللي اتعلمته لمنهجية بتمشي عليها في أي target.

⚖️
Scope أولًا

الـ recon «السلبي» (قراية اللي السيرفر بيبعته، Wayback، البحث) مختلف عن الـ scanning النشط. حتى في الـ bug bounty، الـ subdomains والـ hosts اللي هتلاقيها مش بالضرورة في الـ scope. اقرا الـ policy واشتغل جواها بس.

المنهجية خطوة خطوة

01

اتصفح كمستخدم وBurp شغّال

اعمل حساب، جرّب كل feature (بحث، رفع، دفع، إعدادات). Burp بيبني Site map بكل request. ده أساس كل حاجة بعد كده.

02

اقرا الـ source لكل «نوع» صفحة

view-source: للـ HTML الخام، وتاب Elements للـ DOM بعد الـ JS. دوّر على: <!--، type="hidden"، hidden/disabled، data-*.

03

الفورمز

كل action وmethod وكل name (بما فيها الـ hidden). فيه CSRF token؟ فيه parameters بتتحكم في حاجة حساسة (price، role، user_id، debug، return)؟

04

كل URL في الصفحة

href، src، action، formaction، srcset، CSS url(): الـ paths بتكشف directories، والـ hosts بتكشف subdomains وخدمات خارجية، وmailto: بتكشف إيميلات.

05

ملفات الـ JavaScript

أغنى مصدر: كل fetch/axios/XMLHttpRequest = endpoint، routes الـ SPA (حتى صفحات admin)، feature flags، شروط صلاحيات بتتعمل في المتصفح، وأحيانًا secrets. ودوّر على //# sourceMappingURL=.

06

البصمة التقنية

meta generator، أرقام الإصدارات في أسماء الملفات والـ query (?ver=)، الـ headers (Server، X-Powered-By)، الـ cookies (PHPSESSID، JSESSIONID، ASP.NET_SessionId).

07

الملفات المعروفة

/robots.txt، /sitemap.xml، /.well-known/security.txt (للتواصل الرسمي)، /manifest.json، /crossdomain.xml، وأحيانًا exposures زي /.git/HEAD أو .env أو backup.zip (اختبارها نشط — في الـ scope بس).

08

الماضي

Wayback Machine (web.archive.org) فيه نسخ قديمة من الصفحات وملفات JS — endpoints اتشالت من الواجهة بس ممكن لسه شغّالة في السيرفر.

curl + grep: recon في سطر

# every URL-ish attribute on a page curl -s https://shop.example/ | grep -oiE '(href|src|action|formaction)="[^"]+"' | sort -u # one-line HTML comments curl -s https://shop.example/ | grep -oE '' # hidden inputs curl -s https://shop.example/login | grep -oiE ']+type="?hidden"?[^>]*>' # API paths inside a JS bundle curl -s https://shop.example/static/js/main.4f9c2a.js | grep -oE '"/(api|v[0-9]+|graphql|internal)[^"]*"' | sort -u # does a source map exist? curl -s -o /dev/null -w "%{http_code}\n" https://shop.example/static/js/main.4f9c2a.js.map # secrets-looking strings in downloaded JS grep -RniE 'api[_-]?key|secret|token|passw|bearer' ./js/

الـ Source maps: الكود الأصلي على طبق

الـ JS في الإنتاج بيبقى minified (أسماء متغيرات حرف واحد، سطر واحد). الـ source map (main.js.map) ملف JSON بيربط الكود ده بالكود الأصلي — بتاعة الـ debugging. لو اترفعت على السيرفر، DevTools بيعرض المشروع الأصلي كامل: الملفات، الأسماء، الـ comments، وأحيانًا routes وendpoints مش مستخدمة. علامة وجودها: آخر سطر في الملف //# sourceMappingURL=main.js.map أو header SourceMap.

Impact قبل الإبلاغ

«لقيت API key في الـ JS» لوحدها مش finding. السؤال: تقدر تعمل بيه إيه؟ اختبر بأقل استخدام ممكن ومن غير أي ضرر أو وصول لبيانات حد (مثلًا: endpoint بيرجّع اسم الحساب بس)، ووثّق. keys زي Stripe pk_ أو Google Maps المتقيّد معمولة عشان تبقى عامة. وأي secret حقيقي لقيته: بلّغ بسرعة ومتستخدموش أكتر من اللازم لإثبات الـ impact.

الشروط اللي في المتصفح = خريطة للـ access control

function renderMenu(user) { const items = [{ label: "Orders", href: "/orders" }]; if (user.role === "admin") { // client-side check only! items.push({ label: "Users", href: "/admin/users" }); items.push({ label: "Refunds", href: "/admin/refunds/approve" }); } return items; } // later: fetch("/api/v2/admin/users?limit=100")

الكود ده بيخفي القايمة عن المستخدم العادي — بس قالك بالظبط إيه الـ endpoints بتاعة الـ admin. الخطوة الجاية: تطلب /admin/users و/api/v2/admin/users بـ session مستخدم عادي. لو رجعت داتا = Broken Access Control. القاعدة: إخفاء حاجة في الـ UI ≠ حمايتها.

إيه الـ CMS وإصداره؟ (مثال للصيغة: Drupal 9.4.2)

 `Joomla! 3.9.27` — من الـ generator ومن `?v=3.9.27` في الـ CSS. Joomla 3.x خرج من الدعم الرسمي (أغسطس 2023)، فأي CVE بعد كده مفيش ليه patch رسمي. ومعاه jQuery 1.12.4 قديم جدًا.

إيه الـ host بتاع الـ API اللي الصفحة بتكلمه؟

 `api-dev.megacorp.example` (من `data-api`). كلمة «dev» على host بيكلمه الإنتاج = بيئة تطوير مكشوفة غالبًا أضعف حماية. ومعاه `sso.megacorp.example` من الـ preconnect و`cdn.megacorp.example`. (اتأكد إنهم في الـ scope قبل أي اختبار.)

في الفورم، إيه اسم الـ hidden parameter اللي أول حاجة هتجرّب تغيّر قيمته عشان ممكن يفتح سلوك مخفي؟

 `debug` (من `0` لـ `1` أو `true`). parameters زي `debug` و`test` و`admin` و`dev` ممكن تفتح stack traces أو logs. وكمان `return=/dashboard` يستاهل اختبار open redirect (`return=//evil.example`).

إيه الـ path بتاع الـ endpoint القديم اللي المطوّرين نسيوه في الصفحة؟

 `/services/LegacyAuth.asmx` من الـ HTML comment — SOAP service (`.asmx` = ASP.NET قديم) لـ authentication. الـ endpoints القديمة اللي «المابايل بس بيستخدمها» غالبًا مفيهاش rate limiting أو MFA زي الواجهة الجديدة. وعادة `?wsdl` بيوصفها كاملة.

الـ #admin-tools مخفي. من الـ JS: لازم localStorage.portal_role يساوي إيه عشان يظهر؟ (وفكّر: ده يثبت ثغرة لوحده؟)

 `superuser`. بس ده بيغيّر الـ UI في متصفحك وبس — ده مش ثغرة لوحده. الثغرة الحقيقية تتأكد لما تطلب `/internal/reports/export?format=csv` مباشرة بـ session عادي (أو من غير session) وترجع داتا. الـ JS ادّاك الـ endpoint؛ الـ access control على السيرفر هو اللي بيتختبر.

إيه اسم الملف اللي ممكن يدّيك الـ source code الأصلي للـ JS؟

 `portal.min.js.map` (بيتحسب relative لملف الـ JS: `/js/portal.min.js.map`). لو رجع 200، افتح DevTools → Sources وهتلاقي المشروع الأصلي. وكمان: الـ AWS key ID اللي في الكود — الـ ID لوحده من غير secret مش كفاية للوصول، بس وجوده (والـ TODO) بيقول إن فيه secrets في الـ frontend، فدوّر على باقيها في الـ source map. `robots.txt` فيه `Disallow: /backup-2024/`. ده معناه إيه بالنسبة لك؟ المسار محمي ومحدش يقدر يفتحه المسار مش موجود المطوّر مش عايز محركات البحث تفهرسه — يعني غالبًا موجود ويستاهل تبص عليه (في الـ scope) لازم تتجاهله قانونيًا robots.txt طلب لمحركات البحث مش access control، وكتير بيكشف paths حساسة. `Disallow` مبيمنعش حد. بيطلب من الـ crawlers المحترمة متدخلش — وده بيدّيك hint. لقيت `pk_live_51H…` في JS بتاع صفحة الدفع. ده finding خطير؟ غالبًا لأ — الـ Stripe publishable key معمول عشان يبقى في المتصفح؛ الخطير هو `sk_live_` أيوه critical دايمًا أيوه لأنه بيبدأ بـ live لازم تجرّب تعمل بيه charges اعرف نوع الـ key قبل ما تبلّغ. الـ publishable keys بتعمل tokenization بس. Stripe عنده نوعين: publishable (`pk_`، عام بالتصميم) وsecret (`sk_`، لازم يفضل في السيرفر). وعمرك ما تعمل عمليات مالية حقيقية بـ key لقيته. آخر سطر في `main.js`: `//# sourceMappingURL=main.js.map`. ليه ده مهم؟ ده comment ملوش لازمة بيسرّع التحميل معناه إن الموقع آمن لو الملف `.map` متاح، بيكشف الـ source الأصلي قبل الـ minification (أسماء، comments، routes) الـ source maps في الإنتاج = تسريب للكود الأصلي. نتيجة شائعة في التقارير (severity حسب اللي فيها). الـ source map ملف debugging بيرجّع الكود المضغوط لأصله. لو مرفوع، أي حد يشوف المشروع كامل. الـ JS بيخفي زرار «Delete user» لو `role !== "admin"`. إزاي تتأكد إن فيه ثغرة؟ تغيّر الـ role في localStorage وتشوف الزرار ظهر تبعت الـ request بتاع الحذف مباشرة بـ session مستخدم عادي (على حساب تجريبي بتاعك) وتشوف السيرفر قبله ولا رفضه تقرا الـ CSS مفيش طريقة الـ UI بيتغيّر في متصفحك بس. اللي يحدد الثغرة هو رد السيرفر على request مش مصرّح بيه — واختبره على resources بتاعتك أو تجريبية. ظهور الزرار مش دليل. الدليل إن السيرفر ينفّذ action مكنش المفروض يسمح بيه لصلاحياتك. endpoint اتشال من الواجهة الجديدة السنة اللي فاتت. فين ممكن تلاقيه؟ مستحيل في الـ CSS Wayback Machine (نسخ قديمة من الصفحات وملفات JS) وأدوات زي gau/waybackurls في الـ favicon الأرشيف بيفتكر اللي الموقع نسيه — وكتير الـ backend لسه بيرد على الـ endpoints القديمة. Wayback Machine وأدوات جمع الـ URLs التاريخية بترجّع endpoints قديمة ممكن لسه شغّالة.
