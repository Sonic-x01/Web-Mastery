الـ iframes: صفحة جوه صفحة

<iframe> بيحط مستند كامل (بـ window وDOM وscripts بتوعه) جوه صفحتك: خرايط، فيديوهات، أزرار دفع، widgets. وده بيفتح أسئلة أمنية مهمة: مين يقدر يوصل لمين؟ إزاي تعزل كود مش موثوق؟ وإزاي موقع يخدع المستخدم يدوس على زرار في موقع تاني من غير ما يعرف (clickjacking)؟ — بالمناسبة، كل المعاينات في الكورس ده iframes معزولة.

مين يقدر يلمس مين؟ (Same-Origin Policy)

كل iframe ليه window منفصل. الأب يقدر يوصل للـ iframe بـ iframe.contentWindow، والـ iframe يوصل لأبوه بـ window.parent وللأعلى بـ window.top. بس: لو الاتنين من نفس الـ origin بس يقدروا يقروا ويعدّلوا DOM بعض. لو من origins مختلفة، الـ Same-Origin Policy بتمنع القراية تمامًا، والمسموح بس حاجات محدودة: تغيير الـ location (navigation) وتبادل رسائل بـ postMessage.

الـ sandbox: عزل الكود اللي مش واثق فيه

<iframe sandbox> فاضي = أقصى تقييد: مفيش scripts، مفيش forms، مفيش popups، مفيش navigation للصفحة الأب، مفيش downloads، والمستند بياخد origin «opaque» (فريد، مش بيساوي حتى نفسه) فميقدرش يوصل لأي cookies أو storage. كل كلمة في الـ sandbox «بترفع» قيد واحد:

لو المحتوى اللي جوه الـ iframe من نفس الـ origin بتاع الصفحة، والـ sandbox فيه الاتنين مع بعض، الـ script جواه يقدر يوصل لـ parent.document، يمسك عنصر الـ iframe نفسه، ويـشيل الـ sandbox attribute ويعمل reload — هروب كامل. القاعدة: كود مش موثوق = allow-scripts من غير allow-same-origin (زي معاينات الكورس ده: sandbox="allow-scripts allow-forms")، أو تخدمه من دومين منفصل خالص.

🎯
srcdoc = XSS بالـ entities

قيمة srcdoc attribute، فالـ entities جواها بتتفك، وبعدين الناتج بيتقري كـ HTML كامل. يعني <iframe srcdoc="&lt;script&gt;alert(1)&lt;/script&gt;"> بيشغّل script — وبما إن الـ srcdoc من غير sandbox بياخد origin الصفحة الأب، الـ script يقدر يقرا parent.document.cookie. فلتر بيمنع <script كنص بس، وبيسمح بـ iframe وsrcdoc، هيتخدع.

object وembed (للمعرفة)

<object data="file.pdf" type="application/pdf"> و<embed src="…"> كانوا للـ plugins (Flash، Java) اللي اختفت. لسه بيستخدموا لعرض PDF أحيانًا. 🎯 أمنيًا: <object data="…"> و<embed src="…"> ممكن يحمّلوا HTML أو SVG كمستند كامل (زي iframe) — فلو الفلتر بيمنع iframe ومبيمنعهمش، دول بدايل. والـ CSP بتتحكم فيهم بـ object-src (والأفضل 'none').

Clickjacking (UI redressing)

صفحة المهاجم فيها «طُعم»: زرار مغري زي «Claim prize». الصفحة نفسها بتحمّل الموقع المستهدف (البنك) في iframe. الضحية عاملة login في البنك، فالـ iframe بيتحمّل بالـ cookies بتاعتها ومعروض فيه زرار حقيقي «Delete account». بالـ CSS: الـ iframe بيتحط فوق الطُعم بالظبط، وشفاف تمامًا (opacity: 0). الضحية مش شايفاه خالص. الضحية بتدوس «Claim prize»… والضغطة بتروح للزرار الحقيقي اللي في البنك. أي action بضغطة واحدة (حذف، تحويل، تغيير إعدادات، «Allow») ممكن يتعمل كده.

🎯
إزاي تختبر الـ clickjacking في pentest

(1) بص على الـ response headers للصفحات الحساسة (settings، payments، OAuth «Allow»): فيه frame-ancestors أو X-Frame-Options؟ (2) اعمل PoC صغير زي اللي فوق بـ <iframe src="https://target/…"> — لو الصفحة ظهرت جواه ومحمّلة الجلسة، فهي قابلة للـ framing. (3) الـ finding يبقى مهم لو فيه action حساس بضغطة واحدة؛ صفحة static قابلة للـ framing قيمتها ضعيفة.

postMessage: الكلام المسموح بين الـ origins

// parent page (https://shop.example) → iframe (https://pay.example) frame.contentWindow.postMessage({ amount: 499 }, "https://pay.example"); // ✅ exact target origin // inside the iframe: ALWAYS check who is talking to you window.addEventListener("message", (event) => { if (event.origin !== "https://shop.example") return; // ✅ ignore everyone else charge(event.data.amount); });

الـ postMessage هو الطريقة الرسمية للكلام بين windows من origins مختلفة. الأخطاء الكلاسيكية: الإرسال بـ "*" (أي حد ممكن يستقبل الداتا)، والاستقبال من غير التحقق من event.origin (أي موقع يقدر يبعت أوامر). 🎯 ده مصدر ثغرات DOM XSS وتسريب tokens كتير — هنكسره في الجزء الرابع بعد ما نتعلم JavaScript.
