الـ Encoding والـ Contexts: نفس الحرف بخمس لغات

الصفحة الواحدة فيها كذا «لغة» جوه بعض: HTML، وجواها URLs، وJavaScript، وCSS. كل لغة ليها حروفها الخطيرة وطريقة الـ escaping بتاعتها، والمتصفح بيفك الطبقات دي بترتيب معين. لو فهمت الترتيب ده، هتعرف ليه encoding معيّن بيحمي في مكان وبيفشل في مكان تاني — وهتعرف تفك أي obfuscation في sample خبيث.

من bytes لحروف: الـ charset

الشبكة بتنقل bytes، والمتصفح لازم يعرف يحوّلها حروف إزاي. UTF-8 هو المعيار: الحروف الإنجليزية byte واحد (متوافق مع ASCII)، والعربي 2 bytes، والـ emoji 4. المتصفح بيحدد الـ encoding بالأولوية دي:

3

لو الـ encoding غلط بيحصل «mojibake»: كلمة السر بـ UTF-8 هي الـ bytes D8 A7 D9 84 D8 B3 D8 B1، ولو اتقرت كـ windows-1252 تطلع Ø§Ù„Ø³Ø±. لما تشوف Ø وÙ كتير في نص = عربي UTF-8 اتقري غلط.

🎯
الـ charset سلاح

تاريخيًا: صفحات من غير charset كان ممكن تتقري UTF-7 في Internet Explorer، والـ payload +ADw-script+AD4- (اللي مفيهوش أي <!) يبقى <script>. حديثًا: بحث من SonarSource («Encoding Differentials») أثبت إن صفحات من غير charset معلن ممكن المتصفح يقراها ISO-2022-JP لو المهاجم حقن escape sequences معينة، وده بيبوّظ الـ escaping (مثلًا الـ backslash يتقري ¥) ويفتح XSS. الدفاع بسيط وإجباري: Content-Type: text/html; charset=utf-8 في كل response.

الـ javascript: URLs بتتعمل percent-decode

قبل ما الكود يتنفّذ، جزء ما بعد javascript: بيتعمله URL percent-decode. يعني javascript:%61lert(1) = alert(1)، وjavascript:alert%28document.domain%29 شغّال. والـ URL parser كمان بيشيل الـ tabs والـ newlines من الـ scheme: java&#x09;script: → java⇥script: → javascript:.

مصفوفة الـ contexts: فين الـ input وإزاي تحميه

1 · HTML body
<p>Hello INPUT</p>

الهجوم: <img src=x onerror=…>
الحماية: HTML-encode لـ & < > (و" ').

2 · Attribute بين quotes
<input value="INPUT">

الهجوم: " autofocus onfocus=… أو "><script>
الحماية: encode لـ " و' و& (و< >).

3 · Attribute من غير quotes
<input value=INPUT>

الهجوم: x onmouseover=alert(1) — مسافة كفاية
الحماية: متعملش كده أبدًا: حط quotes دايمًا.

4 · URL attribute
<a href="INPUT">

الهجوم: javascript:alert(1) (مفيش حرف خاص!)
الحماية: parse الـ URL + allow-list للـ scheme (https:)، ثم attribute-encode.

5 · JS string في script
<script>var q='INPUT';</script>

الهجوم: ';alert(1)// أو </script><img …>
الحماية: JS-escape (\xHH) بما فيها <، أو JSON في <script type="application/json">.

6 · Event handler
onclick="go('INPUT')"

الهجوم: &#39;);alert(1)// (الـ entities بتتفك الأول)
الحماية: JS-escape ثم HTML-encode — أو شيل الـ inline handlers.

7 · RCDATA / RAWTEXT
<textarea>INPUT</textarea>

الهجوم: </textarea><img …>
الحماية: HTML-encode (بيمنع </).

8 · CSS
<div style="color: INPUT">

الهجوم: red; background:url(//evil/x) (تسريب/UI redress)
الحماية: allow-list للقيم (^#[0-9a-f]{6}$).

9 · HTML comment
<!-- user: INPUT -->

الهجوم: --><img …> أو --!>
الحماية: متحطش داتا مستخدمين في comments.

🛡️
القاعدة الذهبية: encode حسب الـ context، وفي اللحظة الأخيرة

مفيش «escaping واحد يحمي من كل حاجة». الـ template engines الحديثة (React JSX، Jinja2، Go html/template، Razor) بتعمل HTML-encode أوتوماتيك للنص والـ attributes — والثغرات بتحصل لما المطوّر يكسر ده: dangerouslySetInnerHTML، |safe، {!! !!}، v-html، أو يحط داتا جوه script/URL/handler. لما تعمل code review دوّر على الكلمات دي بالظبط.

Double encoding والـ normalization

  • Double encoding: %253C = %3C بعد decode واحد = < بعد التاني. لو الفلتر بيفك مرة والتطبيق مرتين (أو proxy في النص بيفك) = bypass.
  • Decode بعد الـ validation: أي تحويل بيحصل بعد الفحص (URL-decode، HTML-decode، Base64، lowercase) ممكن يرجّع الحرف الخطير. الترتيب الصح: normalize/decode الأول، validate، وencode وقت الإخراج.
  • Unicode normalization: الـ NFKC بيحوّل ＜ (fullwidth U+FF1C) لـ <. تطبيق بيفلتر وبعدين يعمل normalize = ＜script＞ بقت <script>. وكمان الـ case mapping: "ſ".toUpperCase() = "S".
  • Homoglyphs: а (سيريلي) شبه a — في الدومينات (IDN) وفي أسماء المستخدمين.

🦠 الـ encoding كـ obfuscation في الـ malware

صفحات الـ phishing والـ droppers بتخبّي الـ URLs والكود بطبقات encoding عشان الفلاتر والـ scanners متلاقيش كلمات واضحة. الأشكال اللي هتقابلها:
