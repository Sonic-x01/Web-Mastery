الويب من جوه: المتصفح والسيرفر والـ HTTP

قبل أول tag، لازم الصورة الكبيرة تبقى واضحة: المتصفح بيبعت request، والسيرفر بيرد بـ response فيه HTML، والمتصفح بيحوّل الـ HTML ده لصفحة. كل ثغرة ويب هتقابلها هي في الآخر حاجة غلط في واحدة من المراحل دي — فلازم تعرفها مرحلة مرحلة.

إيه اللي بيحصل لما تكتب URL وتدوس Enter؟ الرحلة كاملة

المتصفح بيـ parse الـ URL: الـ scheme https، الـ host shop.example، الـ path /products، والـ query ?id=7. (الـ URL ليه درس كامل: الدرس 04.) DNS: المتصفح محتاج IP مش اسم. بيسأل الـ resolver فيرجّعله 203.0.113.10. (🎯 الـ subdomains والـ DNS records هي أول خطوة recon في أي pentest.) TCP على port 443، وبعده TLS handshake: السيرفر بيقدّم شهادة (certificate) والطرفين بيتفقوا على مفاتيح تشفير. من هنا أي حد في النص (Wi-Fi، ISP) مش هيقدر يقرا أو يعدّل الكلام. المتصفح بيبعت الـ HTTP request: method + path + headers (منهم Host وCookie). ده النص اللي هتشوفه وتعدّله في Burp طول حياتك المهنية. السيرفر بيشغّل الـ app code (وغالبًا يسأل database)، ويرجّع HTTP response: status code + headers + body فيه الـ HTML. هنا بيحصل أغلب الـ XSS: لو الكود حط input بتاعك في الـ HTML من غير encoding. الـ HTML parser بيقرا الـ bytes ويبني شجرة DOM. وهو بيقرا بيلاقي <link> و<script> و<img> فيبعت requests تانية ليهم. الـ CSS بيتحوّل لـ CSSOM، والـ DOM + CSSOM = render tree → حساب الأماكن (layout) → الرسم (paint). ده اللي بتشوفه. الـ JavaScript بيشتغل: يقدر يغيّر الـ DOM، ويبعت requests (APIs)، ويقرا الـ cookies (لو مش HttpOnly). عشان كده الـ XSS خطير: كود المهاجم بيشتغل بنفس صلاحيات كود الموقع.

شكل الـ HTTP request من جوه نص عادي!

الـ status line فيه رقم (200) ووصف (OK). الـ Content-Type بيقول للمتصفح «اتعامل مع الـ body ده كـ HTML وبالـ encoding ده». وSet-Cookie بيخلّي المتصفح يخزّن cookie ويبعتها تلقائيًا مع كل request جاي للموقع — كده الـ HTTP اللي هو stateless (كل request مستقل) بقى «فاكر» إنك عامل login.

📜
HTTP/2 وHTTP/3

المواقع الحديثة غالبًا بتستخدم HTTP/2 أو HTTP/3: نفس المعاني (methods، headers، status codes) بس متبعتة كـ binary frames مش نص، والـ request line بيتحول لـ pseudo-headers زي :method و:path و:authority. Burp وDevTools بيعرضوهم كأنهم HTTP/1.1 عشان تقراهم بسهولة — فالشكل النصي اللي فوق هو اللي هتشتغل بيه.

🎯
معلومة هتحتاجها في الـ CSRF

فورم HTML عادية تقدر تبعت GET وPOST بس (وmethod="dialog" اللي مبيبعتش request أصلًا). PUT وDELETE وPATCH محتاجين JavaScript (fetch)، والـ JavaScript بيخضع لقيود الـ CORS لو الطلب لموقع تاني. فـ endpoint بيقبل تغييرات بـ POST form عادي هو أول مكان تدوّر فيه على CSRF.

الـ Content-Type: نفس الـ bytes بمعنى مختلف

المتصفح مبيحكمش على الـ response من امتداد الملف في الـ URL. بيحكم من الـ Content-Type. نفس النص <script>alert(1)</script> لو رجع بـ text/html هيتنفّذ، ولو رجع بـ text/plain أو application/json هيتعرض كنص. لو الـ header مش موجود أصلًا، المتصفح بيعمل MIME sniffing (بيخمّن من المحتوى) — وده اتاستغل كتير زمان، والحماية منه header اسمه X-Content-Type-Options: nosniff.

GET /uploads/avatar.png
HTTP/1.1 200 OK
Content-Type: text/html

<script>alert(document.cookie)</script>

لو السيرفر بيحدد الـ type من المحتوى أو من غير قواعد، رفع «صورة» فيها HTML ممكن يبقى stored XSS.

curl: HTTP من غير متصفح

الـ curl بيبعت الـ request ويطبع الـ response خام — مفيش JavaScript بيشتغل ولا parser بيصلّح حاجة. ده بيوريك اللي السيرفر بعته بالظبط:

# -i : print the response headers too curl -i https://shop.example/ # only the headers (HEAD request) curl -I https://shop.example/ # send a form POST, with a cookie, following redirects (-L) curl -i -L -X POST https://shop.example/account/login \ -H "Cookie: lang=ar" \ --data-urlencode "user=omar" --data-urlencode "pass=Sup3r!Secret" # pretend to be a browser / another site curl -i https://shop.example/ -H "User-Agent: Mozilla/5.0" -H "Referer: https://evil.example/"

الـ Proxy: إنت في النص

✏️ تمارين الدرس 01

رتّب المراحل لما تفتح `https://shop.example` لأول مرة: HTTP request ثم DNS ثم TLS ثم TCP TLS ثم DNS ثم TCP ثم HTTP request DNS ثم TCP ثم TLS ثم HTTP request TCP ثم HTTP request ثم DNS ثم TLS الاسم يتحوّل لـ IP (DNS)، بعدين اتصال (TCP)، بعدين تشفير (TLS)، وجوّه القناة المشفّرة يتبعت الـ HTTP request. مينفعش تفتح اتصال TCP من غير IP (يبقى DNS الأول)، ومينفعش تبعت HTTP على HTTPS قبل ما الـ TLS يخلص. ليه الـ `Host` header مهم لدرجة إنه إجباري في HTTP/1.1؟ عشان السيرفر يعرف الـ IP بتاع المستخدم لأن سيرفر واحد (IP واحد) ممكن يشيل مواقع كتير، والـ Host بيقوله أنهي موقع مطلوب عشان الـ TLS يشتغل عشان المتصفح يعرف يحفظ الـ cookies ده الـ virtual hosting. وعشان كده تغيير الـ Host في Burp ممكن يوصّلك لمواقع داخلية على نفس السيرفر، أو يكشف Host header injection. الـ IP بيوصل من طبقة TCP مش من header. الـ Host وظيفته يحدد أنهي موقع من المواقع اللي على نفس السيرفر (virtual hosting). جربت تفتح `/admin` فرجعلك `403 Forbidden`، وجربت `/backup` فرجعلك `404 Not Found`. إيه أدق استنتاج؟ `/admin` غالبًا موجود بس ممنوع عليك، و`/backup` غالبًا مش موجود الاتنين مش موجودين الاتنين موجودين السيرفر واقع بالظبط — الفرق بين 403 و404 معلومة recon قيّمة. (مع ملاحظة إن بعض المواقع بترجع 404 عن قصد لأي حاجة ممنوعة عشان متكشفش وجودها.) 403 معناها «عارف إنت عايز إيه، بس ممنوع» — يعني الـ resource غالبًا موجود. 404 «مش لاقيه». الفرق ده بيستخدم في اكتشاف الـ paths. صفحة بتضيف لينك للـ admin بالـ JavaScript بعد التحميل. فين هتلاقي اللينك ده؟ في `view-source:` بس في الـ response اللي `curl` بيطبعه مش هيظهر في أي مكان في الـ DOM الحي (تاب Elements)، ومنطقه موجود في كود الـ JavaScript نفسه view-source وcurl بيوروك اللي السيرفر بعته قبل أي JavaScript. الـ Elements بيوريك الـ DOM بعد التنفيذ — والمعلومة الحقيقية في ملف الـ JS اللي عمل الإضافة. `view-source` و`curl` بيعرضوا الـ HTML الخام من السيرفر، قبل ما أي JavaScript يشتغل. اللينك اتضاف للـ DOM بعد كده، فهتلاقيه في تاب Elements وفي كود الـ JS. إيه اللي بيحدد إن المتصفح هيعرض الـ response كصفحة HTML ولا كنص؟ امتداد الملف في الـ URL (`.html` أو `.txt`) الـ `Content-Type` header الـ `Host` header الـ status code الـ Content-Type هو الحكم. الامتداد في الـ URL مجرد نص — سيرفر ممكن يرجّع HTML من `/image.png` لو قال `text/html`. المتصفح مبيثقش في الامتداد. بيقرا الـ `Content-Type` (ولو مش موجود بيعمل sniffing، إلا لو فيه `X-Content-Type-Options: nosniff`). فورم HTML عادية (من غير JavaScript) تقدر تبعت أنهي methods؟ أي method: GET وPOST وPUT وDELETE GET بس GET وPOST (و`dialog` اللي مبيبعتش request) POST بس صح. عشان كده الـ CSRF الكلاسيكي بيستهدف endpoints بتقبل GET أو POST عادي، والـ APIs اللي بتطلب PUT/DELETE أو JSON بتحتاج JavaScript (وده بيدخل الـ CORS في الصورة). الـ `method` في الفورم بيقبل `get` و`post` و`dialog` بس. أي قيمة تانية زي `put` بترجع للـ default اللي هو GET. السيرفر رجّع `Set-Cookie: session=7f3a; HttpOnly`. إيه اللي هيحصل بعد كده؟ المتصفح هيخزنها ويبعتها في `Cookie` header مع الـ requests الجاية لنفس الموقع، وJavaScript مش هيقدر يقراها المستخدم لازم يبعتها بإيده هتتبعت مرة واحدة بس JavaScript بس اللي يقدر يقراها ده بالظبط. والـ `HttpOnly` معناها إن `document.cookie` مش هيرجّعها — ده بيصعّب سرقتها بالـ XSS (بس XSS لسه يقدر يعمل requests باسم المستخدم!). `Set-Cookie` بيخلّي المتصفح يخزن الـ cookie ويبعتها تلقائيًا مع كل request مناسب. و`HttpOnly` بتمنع JavaScript من قرايتها (مش العكس).

ده response حقيقي الشكل من موقع اتعمله scan. إيه اسم الـ cookie اللي شايلة الـ session؟

 HTTP/1.1 200 OK Date: Fri, 20 Nov 2026 10:15:02 GMT Server: nginx/1.18.0 (Ubuntu) Content-Type: text/html; charset=UTF-8 X-Powered-By: PHP/7.4.3 Set-Cookie: PHPSESSID=9f2c1b7e0a5d4e3c; path=/; HttpOnly Set-Cookie: theme=dark; path=/ Cache-Control: no-store Content-Length: 1532 دوّر على الـ `Set-Cookie` اللي قيمتها شكلها random وطويلة وعليها `HttpOnly`. والاسم نفسه بيقولك اللغة. `PHPSESSID` هو الاسم الافتراضي لـ session في PHP. القيمة العشوائية + `HttpOnly` = session. أما `theme=dark` فـ preference عادية. لاحظ كمان إن الـ session cookie ناقصها `Secure` و`SameSite` — دي ملاحظات تتكتب في التقرير.

من نفس الـ response اللي فوق: إيه إصدار PHP اللي السيرفر شغّال بيه؟ (الإجابة بالشكل x.y.z)

 فيه header بيفضح لغة الـ backend وإصدارها. الـ `X-Powered-By: PHP/7.4.3` (وكمان `Server: nginx/1.18.0 (Ubuntu)`) = version disclosure. إصدار PHP 7.4 خرج من الدعم في نوفمبر 2022 — فأول خطوة بعدها تدوّر على CVEs للإصدار ده. التوصية في التقرير: شيل الـ headers دي (`expose_php = Off` و`server_tokens off`).

بعد ما دوست Login رجع الـ response ده. الـ next parameter هيودّيك على أنهي path بعد فك الـ encoding؟

 HTTP/1.1 302 Found Location: https://sso.shop.example/login?next=%2Faccount%2Forders Content-Length: 0 `%2F` هي `/` بعد الـ percent-encoding. (جرّب الـ URL Inspector في الدرس 04 أو CyberChef.) `%2F` = `/`، فالـ next = `/account/orders`. الـ parameters اللي زي `next` و`returnUrl` و`redirect` هي أشهر مكان لثغرة open redirect: لو غيّرتها لـ `https://evil.example` والموقع ودّاك هناك بعد الـ login، يبقى عندك ثغرة يستخدمها الـ phishing.
